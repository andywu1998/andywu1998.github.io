# 日历条目 target_id 过期台账：65 条被重建过的日历事件

2026-09-22。这是 ticket 10 的证据表：本地台账 `entity_projection_state` 里有 **65 条**记录的
`target_id`（写出去时的飞书日历事件 id）已经不在日历上——**记录本身都在**，只是当初的事件被重建过、
id 换了。**2026-09-22 决定：全修（B），已执行完**——65 条全部换成现行 id，复跑 0 条待修，
对账里的 `id_stale` 从 65 变成 0。执行的细节与一个副作用见文末「修复执行」。

## 结论

- **对网页没有影响**：网页要的是「这条记录在日历上」这个事实，日期、标题、正文都来自本地，
  `target_id` 只是个「已经发出去过」的标记（`docs/adr/0010`）。
- **只影响两处**：① 对账报告里 id 级永远显示 65 条对不上；② 将来若把某条重新改成要同步、
  又改了正文，事件线会拿旧 id 去 patch 一个不存在的日历事件，记一行 `failed`（不会重复创建）。
- **65 条都有修复依据**：64 条可以用日历描述里的「同步键」链式证明（现行事件描述里的同步键 =
  老账 `config/feishu_calendar_sync.json` 里那条记录的 key，而老账给这条记录的 `event_id` 正是台账里的旧 id）；
  第 65 条是笔记，现行事件描述里的「笔记ID」就是本地笔记 id。
- **分布**：`2026-09` 1 条、`2026-08` 1 条、`2026-07` 16 条、`2026-06` 47 条。

## 为什么会过期

同一份内容在日历上今天是一条**新事件**（描述里还留着老账那条记录的同步键），而台账记的是**老事件**的 id；
老 id 已经不在日历上。证据链（以 2026-06-11 22:40「数据可视化」为例）：

- 日历现在那条事件的描述末尾：`同步键：719263803120097aeaafcd1d`；
- 老账 `config/feishu_calendar_sync.json` 里这个 key 的 `app_link` 带着 `key=fb5908e2-…`；
- 台账里这条记录的 `target_id` 正是 `fb5908e2-…_0`——而日历上没有它。

逐条追「为什么被重建」没有做（台账只留旧 id，没有事件史）。能确定的是：

- 这 65 条全部来自**老账还在用的时期**（老账覆盖 2025-11 … 2026-08），描述里的同步键都是那种 24 位 key；
- 台账状态：**64 条 `synced`、1 条 `failed`**（失败的正是 2026-09 那条笔记，它在日历上另有事件）；
- 换到 SQLite 事件线之后写出去的事件，描述里的同步键是 `evt_xxx`（本地事件 id），台账的 `target_id`
  与日历对得上，**没有一条是过期的**——所以这是个历史遗留面，不会继续扩大。

## 三条路

| | 做什么 | 代价 |
| --- | --- | --- |
| **A 不修** | 只在对账报告里单列这一类（现在就是这样） | id 级永远显示 65；将来改这些记录时会失败一次 |
| **B 全修** | 一次性脚本（默认 dry-run、幂等、差异清单落盘）把 65 条换成现行 id | 要读一次日历（与 ticket 08 同性质，不是运行依赖） |
| **C 只修 2026-06** | 同上，只覆盖 47 条 | 另外 18 条是同一批重建的，没理由只修一半 |

**建议 B。** 一次性、可复算、可回退（改的是本地台账，重跑投影即生效），
修完 id 级重合数从 168 升到 232 左右。

**顺带浮出来一个要你拍的问题**：现在代码里，`withdrawn` 的笔记会**主动从日历上撤下**（`delete`）。
这与「已发出去的一律保留」是冲突的。两条路：

- **保留**（与规则一致）：把笔记线的撤回分支从「删事件」改成「只是不再跟踪」，日历上留着；
- **照旧**（与 registry 意图一致）：标记为 `withdrawn` 的笔记就是该从日历上消失。
